# ADR-0003 — Product-owner-decided Phase 2 MVP baseline

**Status:** Accepted for Phase 2 MVP by product-owner delegation, 2026-11-14. **Repository activation:** integrated by R2-D1-00 on branch `phase-2`; merge/PR evidence is pending. This is an MVP decision baseline, not evidence that its runtime is implemented or tested. Existing accepted ADR-0001/0002 and frozen v1 contracts remain authoritative; the additive Phase 2 OpenAPI extension is authoritative only after the coordinated PR merges. D1 escalates any implementation conflict and never silently overrides v1.

**Decision-making principle:** fastest honest, reproducible real vertical slice; protect against false purchase alerts; no unnecessary third-party services.

- Treat this as the **decided MVP product policy** because the requester delegated selection. D1's contract/security integration PR applies the policies to the real repo and records `MVP-01..20` in current decision log. No new four-person policy meeting required. - **Frozen v1 never edited in place** to satisfy this ADR. Additive public endpoints use versioned extension; incompatible changes require explicit v2 contract. Existing accepted ICP-01/08/13 stay accepted.
- `contracts/phase2/` illustrates a contract change plan; it is not auto-authoritative until merged. Existing service-local DTO fields must be inspected, not guessed.

## Gateway identity and service-forwarding profile

The isolated demo profile has exactly two pre-provisioned users. The browser sends credentials only to `POST /v2/demo/sessions`; successful authentication sets a short-lived `HttpOnly`, `SameSite=Lax` cookie, with `Secure` required under HTTPS. Mutations require an allowed same origin and CSRF protection. Failed authentication is `401`, origin/CSRF denial is `403`, cross-owner or missing resources are indistinguishable `404`, and disabled demo auth is `503`. The browser never stores or receives a bearer token and never supplies an authoritative owner ID.

Gateway strips any client-supplied internal identity/correlation headers, derives the owner from the validated user bearer token or demo session, and creates its own downstream headers. Existing service profiles require both forms below until D1-01 unifies adapters without changing their ownership semantics:

1. For Goal Intelligence, Gateway mints a short-lived ICP-08 service JWT with UUID `sub`, `token_kind=service`, `iss=SERVICE_JWT_ISSUER`, `aud=SERVICE_JWT_AUDIENCE`, and operation scope `gi.session.write`; it adds the validated owner as `X-Authenticated-User-Id` and propagates a validated UUID `X-Correlation-ID`.
2. For current Goal Management public handlers, Gateway mints a short-lived user-context JWT with owner UUID `sub`, `token_kind=user`, `iss=GATEWAY_JWT_ISSUER`, and `aud=GATEWAY_JWT_AUDIENCE`. D1-01 must keep this token server-to-server and must not expose it to browser storage.
3. D4 owner reads are exposed only through Gateway. Their private adapters must use service JWTs with least-privilege operation scopes and a Gateway-derived owner context; no `/internal/` path may be routed publicly.

The implementation handoff reserves these environment-variable names; values remain server-side and must never be committed or logged:

- `GOALPULSE_PROFILE` (`test`, `dev`, or `demo`; no public-production claim)
- `GATEWAY_DEMO_ALLOWED_ORIGIN`
- `GATEWAY_DEMO_SESSION_SECRET`
- `GATEWAY_DEMO_SESSION_TTL_SECONDS`
- `GATEWAY_DEMO_USER_A_ID`, `GATEWAY_DEMO_USER_A_USERNAME`, `GATEWAY_DEMO_USER_A_PASSWORD_HASH`, `GATEWAY_DEMO_USER_A_DISPLAY_NAME`
- `GATEWAY_DEMO_USER_B_ID`, `GATEWAY_DEMO_USER_B_USERNAME`, `GATEWAY_DEMO_USER_B_PASSWORD_HASH`, `GATEWAY_DEMO_USER_B_DISPLAY_NAME`
- Existing `GATEWAY_DEV_JWT_SECRET`, `GATEWAY_JWT_ISSUER`, `GATEWAY_JWT_AUDIENCE`, `SERVICE_JWT_SECRET`, `SERVICE_JWT_ISSUER`, and `SERVICE_JWT_AUDIENCE`

`GATEWAY_DEMO_SESSION_SECRET`, password hashes, and JWT signing secrets are required in demo and have no repository defaults. D1-01 owns concrete TTL bounds, password-hash verification, CSRF token mechanics, rate limiting, and startup failure tests.
